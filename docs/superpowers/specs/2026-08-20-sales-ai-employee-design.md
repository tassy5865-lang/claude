# 営業AI社員 設計スペック

## 目的

ユーザー(田代裕貴氏)自身の受託・フリーランス営業を支援する独立ツール。案件リサーチ、営業文の作成、案件パイプライン管理を1つのWebツールで完結させる。他プロジェクト(AI-OCR等)と同様、単体で使えるツールとして`営業AI社員/`フォルダに構築する。

## 背景・制約

- リポジトリ内の他プロジェクト(AI-OCR、風袋管理データツール等)はすべて「単一HTML + CDN経由React 18 + Babel Standalone + Tailwind CSS」構成、サーバーなし、GitHub Pagesでそのまま公開できる形。本プロジェクトも同じ構成を踏襲する。
- AIエンジンは他プロジェクトのGemini API BYOKパターンとは異なり、**Claude API**を採用(ユーザー指定)。APIキーはブラウザ内入力→localStorageのみに保存、サーバー送信なし(既存プロジェクトと同じBYOK方針)。
- ブラウザから直接Anthropic APIを呼ぶため`anthropic-dangerous-direct-browser-access: true`ヘッダーが必要(公式には本番非推奨だが、個人のBYOKツールとして許容する既存方針を踏襲)。
- リード発掘・個別下調べに必要なWeb検索は、追加の検索APIキーなしで使えるClaude APIのweb_searchツール(サーバー側実行)を利用する。
- 機能は一気に全部作らず、ユーザーが指定した1カテゴリずつ進める(スコープドイテレーション、過去プロジェクトから継続する開発方針)。

## 画面構成(3タブ)

### 1. 案件パイプライン(データの土台)
- 案件/リードの一覧管理: 会社名、ステータス(未アプローチ/提案中/商談中/受注/失注)、次アクション期日、メモ
- 開いた時に期日超過・当日のフォローアップ案件を上部にハイライト表示(フォローアップリマインダー)
- 各案件に紐づく生成履歴(営業文作成タブで生成した文章)やリサーチメモを保存・参照できる

### 2. 案件リサーチ
- **リード発掘モード**: 業界・キーワードを入力 → Claude API(web_searchツール)が引き合いそうな企業候補を理由付きでリストアップ → ワンクリックでパイプラインに新規案件として追加
- **個別下調べモード**: 会社名/URLを入力 → 事業内容・課題・接点になりそうな情報をAIが調査・要約 → パイプラインの既存案件にメモとして保存可能

### 3. 営業文作成(+勝率アドバイス統合)
- パイプラインから案件を選択(またはパイプライン非連携で直接入力)し、文章種別とトーンを指定して生成
  - 文章種別: ①クライアントへの提案・アプローチメール ②見積もり・提案書としての文章 ③フォローアップ・返信文
- 案件を選択した場合、会社名・リサーチメモ・過去のやり取り履歴を自動でプロンプトに含めて生成
- 生成結果は編集可能なテキストとして表示、パイプラインの案件履歴に保存可能
- **勝率アドバイス**: 生成時、パイプライン内の「受注」「失注」ラベル付き過去案件の傾向(あれば)を踏まえ、AIがトーン・構成の改善点をアドバイス欄に表示。データが少ない初期は一般的なアドバイスにフォールバックする

## データモデル(localStorage)

- `案件` (パイプラインの行): `{ id, 会社名, ステータス, 次アクション日, メモ, リサーチ情報, 生成履歴: [{種別, トーン, 本文, 作成日}] }`
- `APIキー・使用モデル設定`: 他プロジェクトと同様、画面右上の設定アイコンから入力・保存(未設定時は赤丸バッジ表示)

## 実装順序

1. **案件パイプライン**: データの土台となるCRUD機能(一覧・追加・編集・削除・ステータス変更・フォローアップハイライト)
2. **営業文作成**: Claude API連携の確認を兼ねて、パイプライン案件選択→文章生成→保存、および勝率アドバイスまで実装
3. **案件リサーチ**: Claude API web_searchツールを使ったリード発掘・個別下調べ、パイプラインへの連携

各カテゴリはユーザーの指示を受けてから着手する(一括実装しない)。

## エラーハンドリング・テスト方針

- APIキー未設定時は各AI機能ボタンを無効化し、設定を促すバッジ表示(既存プロジェクトのパターンを踏襲)
- Claude API呼び出し失敗時はエラーメッセージを表示し、入力内容は保持(再試行可能にする)
- localStorage保存はブラウザ完結のため、バックアップ手段(エクスポート機能等)の要否は各カテゴリ実装時に必要に応じて検討する
- UIでの動作確認はブラウザでの実地確認を基本とする(自動テストは各プロジェクトの既存方針を踏襲し、必要に応じて検討)
