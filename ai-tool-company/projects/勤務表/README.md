# 勤務表(シフト共有ツール)

管理者が月間のシフトをまとめて作成し、スタッフ全員がスマホ・PCなど別々の端末からいつでも最新のシフトを確認できるツールです。

- ファイル本体: `src/index.html`(このファイル1枚だけで動作します)
- データの保存先: Google Firebase(Firestore)
- 公開方法: これまでの社内ツール同様、GitHub Pages等の静的ホスティングにそのまま置けます

---

## 🔴 本運用の前に経営者の方へ必ずお読みください(重要なセキュリティ上の制約)

このツールは **氏名を含むスタッフの個人情報** をクラウド(Firestore)に保存します。
現在のMVP版には、以下の重大な制約があることを **必ず理解した上で** 運用を開始してください。

> **現状: シフトデータの書き込み・削除は、URLとFirebase設定値さえ分かれば「共通パスワードを知らない第三者でも」技術的には可能な状態です。**
>
> 理由: このツールはサーバー(バックエンド)を持たない静的HTML1枚の構成です。管理者モードの共通パスワードは
> `index.html` のソースコードに直接書かれており、GitHub Pages等で公開すると **誰でもソースを閲覧してパスワードや
> Firebaseの接続情報を読み取れます**。そのため、Firestore側のセキュリティルールでパスワードを再検証するような
> 仕組みを追加しても、その検証用の値自体が同じ理由で公開されてしまい、本質的な防御にはなりません
> (静的サイトのみの構成で「真に秘密の値」を扱うことはできないため)。
> 現在のFirestoreルールは `allow write: if true`(誰でも書き込み可)のままです。
>
> **これが意味すること**: 悪意のある第三者が、全スタッフの氏名・勤務時間を改ざん・削除できてしまう可能性があります。
> 共通パスワードは「社内の人が誤ってうっかり編集してしまう事故」を防ぐだけのものであり、
> 悪意ある外部者に対するセキュリティ対策にはなっていません。
>
> **本運用(実際の従業員の個人情報を継続的に扱う運用)を始める前に、必ず次のいずれかを行ってください。**
> 1. 下記「手順3」に記載の **Firebase Authentication への移行**(推奨)を行い、Firestoreルールを
>    `allow write: if request.auth != null` に変更してから運用を開始する。
> 2. 移行が難しい場合は、上記のリスクを経営者ご自身が理解・許容した上で、限定的な運用(公開URLを社内関係者以外に
>    広めない、機密性の高くないダミー的な運用に留める、等)にとどめる、という**明示的な判断**を行ってください。
>
> このツールの開発チーム(developer/QA)としては、個人情報を扱う本運用での使用は、
> Firebase Authenticationへの移行が完了するまでは推奨しません。

**経営者判断の記録(2026-08-11)**: 上記2「限定的な運用(試験運用)」を選択。当面は以下のルールで運用する。
- 公開URLを社内関係者以外に広めない
- 正式なシフトデータは別途(紙・Excel等)バックアップを保持し、本ツールへの依存度を試験的な範囲にとどめる
- Firebase Authenticationへの移行は、本格運用へ切り替えるタイミングで改めて検討する

## 1. 使い始めるために必要な準備(初回のみ)

このツールは「複数の端末でシフトを共有する」ために、Googleの無料クラウドサービス **Firebase** を使います。
利用には最初に一度だけ、Firebaseプロジェクトの作成と設定値のコピペが必要です。難しい操作はありません。

### 手順1: Firebaseプロジェクトを作成する

1. [https://console.firebase.google.com/](https://console.firebase.google.com/) にGoogleアカウントでログインします。
2. 「プロジェクトを作成」をクリックし、プロジェクト名(例: `kinmuhyo-shift`)を入力して進めます。
   - Googleアナリティクスは不要であれば無効のままで構いません。
3. プロジェクトが作成できたら、プロジェクトのトップ画面で「ウェブアプリを追加」(`</>` アイコン)をクリックします。
4. アプリ名を適当に入力(例: `勤務表`)し、「Firebase Hosting」の設定は不要なのでチェックを入れずに進めます。
5. 表示される `firebaseConfig` という設定オブジェクトをコピーします。以下のような形です。

```js
const firebaseConfig = {
  apiKey: "AIzaSy...",
  authDomain: "kinmuhyo-shift.firebaseapp.com",
  projectId: "kinmuhyo-shift",
  storageBucket: "kinmuhyo-shift.appspot.com",
  messagingSenderId: "1234567890",
  appId: "1:1234567890:web:abcdef123456"
};
```

### 手順2: Firestore データベースを有効化する

1. Firebaseコンソール左メニューの「構築」→「Firestore Database」を開きます。
2. 「データベースの作成」をクリックします。
3. ロケーションは日本に近いリージョン(例: `asia-northeast1` 東京)を選択します。
4. セキュリティルールの初期選択は「テストモード」でも「ロックモード」でもどちらでも構いません(次の手順3で上書きします)。

### 手順3: セキュリティルールを設定する

Firestoreの「ルール」タブを開き、以下の内容を貼り付けて「公開」をクリックしてください(MVP版の推奨ルール)。

```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    // スタッフ一覧・シフトデータは全員が閲覧可能
    // 書き込みはアプリのUI側の共通パスワードでロックしているが、
    // ルール上は誰でも書き込み可能な状態になっている点に注意(下記「セキュリティに関する重要な注意」を参照)
    match /staff/{staffId} {
      allow read: if true;
      allow write: if true;
    }
    match /shifts/{shiftId} {
      allow read: if true;
      allow write: if true;
    }
  }
}
```

> ⚠️ **セキュリティに関する重要な注意(QAレビュー要確認事項)**
>
> このツールの「管理者モード」は、あらかじめコード内に埋め込んだ共通パスワードを
> 入力することで切り替わる **簡易的な仕組み** です(spec.md の経営者確認事項の回答どおり)。
>
> しかし、このツールは GitHub Pages のような公開の場所にホスティングする前提のため、
> **`index.html` のソースコードは誰でも閲覧でき、埋め込まれた共通パスワードや
> Firebaseの設定値(apiKey等)もすべて見えてしまいます。**
> そのため、上記のセキュリティルール(`allow write: if true`)は
> 「知識のある第三者が直接Firestore APIを叩けば、パスワードを知らなくても
> 書き込み・削除ができてしまう」という状態です。共通パスワードは
> **「うっかり編集の防止」以上のセキュリティ効果はない** とご理解ください。
>
> **より安全にしたい場合の改善案(将来の拡張候補)**
> 1. Firebase Authentication を有効化し、管理者用のメールアドレス+パスワードを1つ発行する。
> 2. コード側は共通パスワードの文字列比較ではなく `signInWithEmailAndPassword()` を使うように変更する。
> 3. セキュリティルールを以下のように変更し、ログインしていない人からの書き込みをFirestore側で本当に拒否する。
>    ```
>    match /staff/{staffId} {
>      allow read: if true;
>      allow write: if request.auth != null;
>    }
>    match /shifts/{shiftId} {
>      allow read: if true;
>      allow write: if request.auth != null;
>    }
>    ```
> この改善はサーバーコード(Cloud Functions等)の追加が不要で、比較的小さな変更で実現できるため、
> **本運用(実際の従業員の個人情報を継続的に扱う運用)を開始する前に対応することを強く推奨します。**
> 詳しくは本READMEの冒頭「🔴 本運用の前に経営者の方へ必ずお読みください」を参照してください。

### 手順4: 設定値をコードに貼り付ける

`src/index.html` をテキストエディタで開き、`<script type="module">` 内にある以下の部分を、手順1でコピーした値に書き換えてください。

```js
const firebaseConfig = {
  apiKey: "YOUR_API_KEY",
  authDomain: "YOUR_PROJECT_ID.firebaseapp.com",
  projectId: "YOUR_PROJECT_ID",
  storageBucket: "YOUR_PROJECT_ID.appspot.com",
  messagingSenderId: "YOUR_SENDER_ID",
  appId: "YOUR_APP_ID"
};
```

同じ場所の少し下にある共通パスワードも、運用開始前に必ずご自身の値に変更してください。

```js
const ADMIN_PASSWORD = "shift-admin-2026"; // ← 運用前に必ず変更する
```

設定が完了すると、ページを開いたときに表示されていた「Firebaseの設定が完了していません」という警告が表示されなくなります。

## 2. 使い方

### 閲覧モード(初期状態・スタッフ向け)
- 「全員のシフト」タブ: 1ヶ月分のシフトを、日付×スタッフの表形式で確認できます。
- 「個人ビュー」タブ: スタッフ名を選ぶと、その人の1ヶ月分のシフトだけを見やすいリスト形式で確認できます。
- 編集はできません(見るだけ)。

### 管理者モード
- 右上の「管理者モードに切替」ボタンから共通パスワードを入力すると切り替わります。
- 「スタッフ管理」ボタンから、スタッフの氏名の登録・編集・削除ができます。
- シフト表・個人ビューのセルをクリックすると、その日・その人のシフトを編集できます。
  - ステータスは「勤務」「遅刻予定」「休み」「有給」の4種類です。
  - 「勤務」「遅刻予定」を選んだ場合のみ、開始・終了時刻(30分単位)を選べます。
  - 備考欄に「希望休」等の自由なメモを残せます。
- 保存すると、他の端末で同じページを開いている全員の画面にもリアルタイムで反映されます。

## 3. データ構造(開発者向けメモ)

Firestoreのコレクション構成は以下の通りです。

- `staff`(スタッフ一覧)
  - ドキュメントごとに `{ name: 氏名, order: 表示順, createdAt: 作成日時 }`
- `shifts`(シフト)
  - ドキュメントID: `${日付(YYYY-MM-DD)}_${スタッフID}` という規則の文字列(1人1日1件に固定するため)
  - フィールド: `{ staffId, date, status(work/late/off/paid), startTime, endTime, note, updatedAt }`

スタッフを削除しても、そのスタッフに紐づく過去の `shifts` ドキュメントは自動削除されません(表示上見えなくなるだけ)。データを完全に消したい場合は、Firebaseコンソールから該当ドキュメントを手動で削除してください。将来的に一括削除処理を追加する余地があります。

## 4. 料金について

Firebaseの無料プラン(Sparkプラン)には以下のような上限がありますが、スタッフ10〜30名規模のシフト共有用途であれば十分に無料枠内に収まる見込みです。

- Firestore: 1日あたり読み取り5万回・書き込み2万回など
- 想定利用量: 管理者が1日に数十回書き込み、スタッフ数十人が1日に数回閲覧する程度

利用量が大きく増える場合はFirebaseコンソールの「使用量とお支払い」で確認してください。
