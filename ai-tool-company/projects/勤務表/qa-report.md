## 0. 再レビュー(2026-08-11) — 前回致命的指摘3件への対応確認

### 0-1. 初期表示バグ(旧3-1) → **修正確認: OK**

- `init()`(446-473行)内、`bindStaticEvents()`等の直後・Firebase接続処理より前に `switchViewType(state.viewType);`(455行)が追加されていることを確認した。

### 0-2. 格納型XSS(旧2-2) → **修正確認: OK**

`renderCellContent()`(734-747行)を確認した。

```js
function renderCellContent(shift){
  if (!shift) return `<span class="empty-cell">-</span>`;
  const isKnownStatus = Object.prototype.hasOwnProperty.call(STATUS_LABEL, shift.status);
  if (!isKnownStatus) return `<span class="empty-cell">-</span>`;
  const statusClass = escapeHtml(shift.status);
  const label = escapeHtml(STATUS_LABEL[shift.status]);
  const time = STATUS_NEEDS_TIME[shift.status]
    ? `<br>${escapeHtml(shift.startTime)}-${escapeHtml(shift.endTime)}`
    : "";
  return `<span class="badge ${statusClass}">${label}</span>${time}`;
}
```

- 報告通り、`status`は`STATUS_LABEL`(`work/late/off/paid`)のホワイトリスト外なら`isKnownStatus`が`false`となり、以降を描画せず`empty-cell`として扱う検証が追加されている(739-740行)。
- ホワイトリストを通過した`status`、および`startTime`/`endTime`は全て`escapeHtml()`を経由してから`innerHTML`相当の文字列に埋め込まれている(741,742,744行)。
- 旧レポートで示した概念実証(`startTime`に`<img src=x onerror=...>`を注入)は、①`status`がwhitelist外なら描画自体されない、②`status`がwhitelist内でも`startTime`は`escapeHtml()`を通るため`<`等が実体参照化されテキストとして無害化される、の二重の理由で成立しなくなっていることをコード上確認した。
- `node --check`で該当スクリプト部分の構文エラーがないことも確認済み。HTML内`<div>`開閉数も39/39で一致しており、今回の修正によるマークアップ崩れもない。

**0-1・0-2はいずれも致命的指摘に対する修正として妥当であり、再現条件が成立しないことをコードレベルで確認できた。**

### 0-3. Firestore書き込みルール開放(旧2-1)への対応方針の評価

developerは、コードを修正せず`README.md`冒頭(11-37行)に警告ブロックを新設する対応にとどめた。理由は「静的HTML構成ではクライアント埋め込みトークンに実効的な防御力がない」というもの。**QAとしてこの技術的主張自体は妥当と判断する。** 理由を以下に述べた上で、それでも「対応完了」とは扱わず、リリース可否には条件を付す。

**技術的妥当性の検討**:
- サーバー(バックエンド)を一切持たない静的HTML1枚構成において、Firestoreセキュリティルール側で「クライアントが送ってきた値」(例: 別の共通パスワードやトークンをリクエストに含めてルールで照合する案)を検証しても、その照合対象の値自体が`index.html`のソースに書かれている以上、閲覧者全員に公開される。つまり「秘密の値をルールで検証する」という設計そのものが、この構成では成立しない。これは実装の巧拙の問題ではなく、**「クライアントのみでは真の秘密を保持できない」という暗号論的に自明な制約**であり、developerの説明は技術的に正しい。
- 一方で、`request.auth != null`(Firebase Authenticationを使うルール)が有効な理由は、パスワード文字列の比較ではなく、Firebase側のサーバーがID/パスワードを検証し、**クライアントが偽造できない署名付きトークン(IDトークン)** を発行する点にある。これは「クライアント埋め込みの秘密」とは根本的に性質が異なるため、developerが本命の対策として提示している点も妥当。
- つまり0-2(XSS)は「実装バグ」であり数行の修正で解消できたのに対し、旧2-1は**「バックエンドを持たない」というアーキテクチャ選択そのものに起因する制約**であり、コードレビューで見つけて数行直して終わる性質の指摘ではない。この点でdeveloperが「コード修正ではなく方針を明示する」という対応を選んだこと自体は、技術的に筋が通っている。

**ただし、これで問題が解決したわけではない点を明確にする**:
- README警告文を追加しても、**Firestore側のルールは`allow write: if true`のままであり、氏名・勤務時間という個人情報を誰でも書き換え・削除できる状態は技術的に一切変わっていない。** これは「説明責任を果たした」ことと「リスクが消えた」ことは別問題であり、混同してはならない。
- 警告文の位置(README冒頭、手順1より前)・内容(具体的な攻撃可能性、被害の説明、二択の対応案の提示)は経営者に伝わる書き方になっており、この点は評価できる。

**QA評価(結論)**: developerの判断(コード修正でなくリスク明示にとどめた)は、技術的根拠が正しく、対応として不合理ではない。ただし「対応完了」ではなく「未解決のリスクを経営者の意思決定に委ねた」状態であるため、以下の条件を満たさない限りリリース可としない。

**リリース可とするための条件**:
1. **経営者が本README冒頭の警告ブロック(11-37行)を読み、対応方針(①Firebase Auth移行、②限定運用でのリスク許容のいずれか)を明示的に選択したことを、口頭でも記録でも構わないので確認すること。** 「READMEに書いてあるから良い」ではなく、実際に経営者に読ませ、意思決定させることが必須条件。
2. 経営者が②(限定運用でのリスク許容)を選ぶ場合、少なくとも以下を運用ルールとして明文化すること:
   - 公開URLを社内関係者以外に共有・拡散しない(検索エンジンインデックスされない設定を含む)。
   - 実在従業員の氏名を使う「本運用」ではなく、まずは試験運用(ダミー名 or 少人数の同意を得た試用)から始める、または本運用する場合はデータ改ざん・消失が発生し得ることを前提に、シフトの正データを別途(紙・Excel等)保持しておく。
   - Firebase Authenticationへの移行を「いつまでに行うか」の目安時期を経営者と合意しておく(無期限の先送りにしない)。
3. ①(Firebase Auth移行)を先に行う場合は、移行後のルール(`allow write: if request.auth != null`)適用とログイン動作の確認をもって、この条件は満たされたものとする。
4. 上記1〜3のいずれも満たされない状態(README警告文があるだけで経営者の意思決定も運用ルールもない状態)での実運用開始は、引き続き推奨しない。

## 2. セキュリティ・データ取り扱い(重点確認事項)

氏名・勤務時間という個人情報をクラウド(Firestore)に保存する構成であるため、最も重点的にレビューした。**致命的な指摘が2件、密接に関連しているため合わせて報告する。**

### 2-1. Firestoreの書き込みルールが全世界に開放されている(致命的)

- README.md記載のMVP推奨ルール(43-64行)は `allow write: if true` であり、developerも懸念として明記している通り、`index.html`のソースは誰でも閲覧できるためAPIキー・プロジェクトIDも公開情報になる。
- **判断**: これは「MVPとして許容範囲」ではなく**致命的**と判定する。理由:
  1. 氏名という個人情報を含むデータへの書き込み・削除権限が、パスワードを知らない不特定多数(URLとFirebase設定値さえ分かれば誰でも)に事実上開放されている。
  2. 「うっかり編集防止」を超えて、悪意ある第三者が全スタッフの勤務データを改ざん・全削除できる。業務(シフト運用)そのものを妨害できる状態。
  3. 下記2-2のXSS問題と組み合わさることで、単なるデータ改ざんに留まらず「閲覧者のブラウザ上での任意コード実行」まで到達可能であり、影響範囲がさらに深刻化する。
- developer/READMEが提案しているFirebase Authenticationへの切替案(README 79-94行、`request.auth != null`によるルール変更)は妥当な対策であり、**本運用開始前に必須の対応**とすることを推奨する。

### 2-2. 出力エスケープ漏れによる格納型XSS(致命的・新規指摘)

コードレビューで新たに発見した、2-1の問題と組み合わさると深刻化する不具合。

**該当箇所**: `src/index.html` 728-733行 `renderCellContent()`
```js
function renderCellContent(shift){
  if (!shift) return `<span class="empty-cell">-</span>`;
  const label = STATUS_LABEL[shift.status] || shift.status;
  const time = STATUS_NEEDS_TIME[shift.status] ? `<br>${shift.startTime}-${shift.endTime}` : "";
  return `<span class="badge ${shift.status}">${label}</span>${time}`;
}
```

- 他の箇所(スタッフ名: 649,702,782,857行、備考: 756行)はすべて`escapeHtml()`を通してから`innerHTML`に埋め込んでいるが、**`shift.status`・`shift.startTime`・`shift.endTime`だけエスケープされずに直接`innerHTML`へ挿入されている。**
- 通常のUI操作(ラジオボタン・プルダウンからの入力)では`status`は`work/late/off/paid`の固定値、時刻もプルダウンの固定値しか入らないため顕在化しないが、2-1のルール(`allow write: if true`)によりFirestoreへ直接任意のデータを書き込める以上、この経路は現実的な攻撃対象になる。

**再現手順(概念実証、実機検証は環境上未実施)**:
1. 現状のMVP推奨セキュリティルール(`allow write: if true`)が適用された状態を前提とする。
2. 攻撃者が`index.html`のソースから`firebaseConfig`(apiKey/projectId等、公開情報)を取得する。
3. Firestore Web SDKまたはREST APIを使い、`shifts`コレクションへ次のようなドキュメントを直接書き込む(パスワード不要、UIも経由しない):
   ```json
   { "staffId": "<実在するスタッフID>", "date": "2026-08-15",
     "status": "work",
     "startTime": "<img src=x onerror=alert(document.cookie)>",
     "endTime": "18:00" }
   ```
4. **期待する動作**: 不正な文字列が保存されても、画面上ではテキストとして無害に表示されるべき。
5. **実際の動作**: 該当日・該当スタッフのシフトを表示した全ユーザー(管理者・閲覧者いずれも)のブラウザ上で、`onerror`に書かれたスクリプトが実行される(格納型XSS)。

**影響**: 2-1と合わせると、第三者が「勤務データの改ざん」だけでなく「シフト表を見た全社員のブラウザ上での任意コード実行」まで到達できる。将来Cookie窃取・フィッシング誘導・画面改ざん等に悪用され得るため、致命的と判定する。

**推奨対応**: `label`・`shift.startTime`・`shift.endTime`を他の箇所と同様`escapeHtml()`に通す。加えて`shift.status`がホワイトリスト(`work/late/off/paid`)外の値の場合はそもそも描画しない/`empty-cell`扱いにするなど、値の検証も入れることが望ましい。修正自体は数行で完結する軽微な改修であり、2-1のFirebase Auth移行を待たずに即座に対応可能。

### 2-3. 共通パスワード方式そのものについて

- spec.md 7章で経営者が明示的に確定した仕様であり、方式自体(共通パスワードでの簡易モード切替)は仕様適合。
- ただしREADMEの警告文(66-94行)は正確かつ十分に「これは秘密にならない」旨を経営者に伝える内容になっており、developerの説明責任は果たされている。QAとして問題視するのは共通パスウード方式そのものではなく、**Firestoreルール側でも制御していない(2-1)**点である。

## 3. その他の不具合・改善点

### 3-1. 初期表示でカレンダー表・個人ビューが表示されない(致命的)

**該当箇所**: `src/index.html` 287行・299行、636-644行、446-467行、469-499行

- `#allView`と`#personalView`はHTML上初期状態で`style="display:none;"`(287,299行)。
- これを`display:block`に切り替えるのは`switchViewType()`(636-644行)のみ。
- `switchViewType()`はタブボタンのクリックイベント(534-535行)からしか呼ばれておらず、`init()`(446-467行)や`onSnapshot`のコールバック(469-499行、データ取得完了時)からは一度も呼ばれていない。

**再現手順**:
1. Firebaseの設定を正しく入力し、`index.html`をブラウザで開く。
2. 「読み込み中...」の表示が消えるまで待つ(データ取得完了)。

**期待する動作**: 「全員のシフト」タブがアクティブな状態で、日付×スタッフのカレンダー表がそのまま表示される。

**実際の動作**: ヘッダー・ツールバー・凡例・フッターは表示されるが、本来カレンダー表が入るはずの領域が空白のまま何も表示されない。ユーザーが「全員のシフト」または「個人ビュー」タブを一度クリックして初めて表が現れる。

**重大度**: 致命的。仕様の必須機能3「月間カレンダー表示」が、ページを開いた直後は事実上機能しておらず、非エンジニアのスタッフが見た場合「ツールが壊れている/データが空」と誤解し離脱する可能性が高い。管理者・スタッフ双方の全セッションに影響する。

**推奨対応**: `init()`内でFirestore購読開始前後、または最初の`onSnapshot`コールバック内で `switchViewType(state.viewType)` を一度呼び出す(あるいは単純に`#allView`の初期インラインstyleを削除する)。1〜2行で修正可能。

### 3-2. 「全員のシフト」表に備考(note)が表示されない(軽微)

- `renderAllView`(688-726行)では`renderCellContent(shift)`のみを描画し、`shift.note`を表示していない。一方`renderPersonalView`(735-766行、756行)では備考を表示している。
- 例えば「休み」の理由(希望休/通院等)を備考に入れても、全員が見る共有カレンダーでは分からず、該当スタッフの個人ビューを開かないと確認できない。spec.mdの必須要件違反ではないが、README・developerの実装意図(「備考欄に希望休等のメモを残せる」)からすると、共有カレンダー上でも見えた方が実用性が高いと考えられる。改善候補として提示。

### 3-3. スタッフ削除時にシフトデータが孤立する(軽微・仕様上許容)

- README(149行)に明記の通り、スタッフ削除時に紐づく`shifts`ドキュメントは自動削除されない。確認ダイアログ(876-877行)にもその旨明記されており、ユーザーに伝わる設計になっている。MVPとして許容範囲と判断(致命的な指摘はしない)。ただしFirebaseコンソールでの手動削除は非エンジニアの経営者には荷が重い可能性があり、将来の一括削除機能追加は妥当な拡張候補。

### 3-4. 日をまたぐ勤務(夜勤等)を表現できない(軽微)

- `onShiftSave`(805-833行)で`startTime >= endTime`の場合は保存不可(811-814行)。そのため「22:00〜翌6:00」のような日またぎシフトは登録できない。spec.mdに夜勤の言及はなく対象外業種(小売・飲食の通常シフト等)であれば問題にならないが、業種によっては制約になり得るため、経営者に一言確認しておくことを推奨。

### 3-5. スタッフ管理モーダルを開いている間の他端末からの追加がリアルタイム反映されない(軽微)

- `subscribeStaff`のコールバック(469-480行)は`populateStaffSelect()`と`renderAll()`のみ呼び、モーダル内リスト`renderStaffManageList()`は`btnStaffManage`クリック時・自身の追加/削除成功時にしか再描画されない(548-551,903,880行)。複数管理者が同時に操作する運用がある場合、モーダルを開いたまま待っていると他者の変更が反映されず古い一覧を見続けることになる。MVP規模(管理者は通常1〜数名)では影響は小さいと判断し軽微とする。

### 3-6. Firestore全件購読(月次フィルタなし)(軽微・現状は許容)

- `subscribeShifts`(482-499行)はコレクション全体を購読しており、コメントでも意図的な判断と明記されている。スタッフ10〜30名・月間規模であれば無料枠内で問題ないと判断できるが、運用年数が経ちシフト履歴が蓄積した場合は読み取り件数が線形に増える。将来的な最適化候補として記録しておく。

## 5. リリース可否の結論(2026-08-11 再レビュー後・最終)

### 5-1. 初回レビュー時点の結論(参考・旧版)

**現状は「リリース不可」と判定する。** 致命的な指摘が3件(2-1, 2-2, 3-1)あり、いずれもMVPとして見過ごせない。

- **3-1(初期表示バグ)** は必須機能そのものが動かない不具合であり、修正必須。これがある限り「見るだけで完結する画面」という設計方針(spec.md 2章)を満たせない。
- **2-1(Firestore書き込み無制限)と2-2(XSS)** は、個人情報(氏名・勤務時間)を扱うツールとして許容できない。特に2-1単体であれば「MVPとしての限定リリース+経営者への注意喚起」という判断もあり得たが、2-2との組み合わせにより「データ改ざん」から「閲覧者ブラウザでの任意コード実行」まで到達可能な状態になっており、単なる情報漏えいリスクを超える。この2点は少なくとも次のいずれかの対応が完了するまでリリースを見送るべき:
  - 最低限: 2-2(エスケープ漏れ)を修正する(数行の改修で即対応可能)。
  - 本運用に進める条件: 2-1についてFirebase Authenticationへの切替(README記載の改善案)を行い、Firestoreルールを`allow write: if request.auth != null`相当に変更する。

**限定リリースの是非について**: 「経営者に伝えた上での限定リリース」という選択肢も検討したが、今回は推奨しない。理由は、3-1により通常利用でカレンダーが表示されない不具合が併存しており、セキュリティ以前に機能として体験できない状態であること、また2-2のXSSは経営者に「書き込みが誰でもできる」ことを伝えても防げない性質の不具合(実装バグ)であり、事前説明だけでリスクを許容できる話ではないため。

**再レビュー条件**: 3-1・2-2の修正(いずれも小規模な改修)、および2-1についての対応方針(Firebase Auth移行、または少なくとも経営者への正式なリスク説明と限定運用の合意)が整った時点で、developerからの再提出を受けて再度QAレビューを行う。

### 5-2. 再レビュー(2026-08-11)後の最終結論

**「条件付きリリース可」と判定する。**

- **旧3-1(初期表示バグ)・旧2-2(XSS)は、いずれも修正が正しく反映されていることをコードリーディングで確認した(0-1・0-2参照)。** 前回「機能として体験できない」「事前説明だけでは防げない実装バグ」として限定リリースすら否定した2つの根拠は、両方とも解消されている。
- **旧2-1(Firestore書き込みルール開放)は、コードは修正されず、README冒頭の警告ブロックによるリスク明示にとどまっている。** 0-3で検討した通り、developerの技術的判断(静的HTML構成ではクライアント側トークンに実効的な防御力がない)自体は妥当であり、これは「サボった」のではなく「バックエンドを持たないアーキテクチャの構造的な限界」に起因する。しかし、**Firestore上の個人情報(氏名・勤務時間)が誰でも書き換え・削除できる状態そのものは、README警告文を追加しても技術的には一切変わっていない。**
- したがって、単純な「リリース可」ではなく、**0-3に記載した4条件(経営者による警告文の確認と方針選択、限定運用時の運用ルール明文化、Auth移行時期の目安合意、いずれも満たさない状態での実運用開始をしないこと)を満たすことを条件としたリリース可**とする。この条件は「コードの修正」ではなく「経営者の意思決定と運用ルールの整備」に関するものであるため、developerへの差し戻しではなく、**PM/経営者への申し送り事項**として扱うことを推奨する。

**総括**: 前回致命的指摘3件のうち、実装バグに起因する2件(初期表示・XSS)はいずれも的確に修正されたことを確認した。残る1件(Firestore書き込み開放)は実装では解決不可能な構造的制約であり、developerの「コードで解決したふりをしない」判断は技術的に誠実である。QAとしては、この点を「未修正」として機械的にリリース不可とするのではなく、**「経営者が正しくリスクを認識し、意思決定した上で運用する」という条件下でのリリースを可とする**のが妥当と判断する。
