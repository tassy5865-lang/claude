# 勤務表 spec.md

> **改訂履歴**: 初版は「個人が出退勤を打刻する勤怠記録ツール」として作成したが、経営者より
> 「シフトを組むツールでデータを複数に共有」と明確な訂正が入ったため、本バージョンで
> **管理者がシフトを作成し、複数人・複数端末で共有するツール** として仕様を全面的に書き直した。

## 1. 目的・背景
- 現状、スタッフの勤務シフト(誰がいつ・何時から何時まで働くか)を紙やExcelで作成・共有しており、作成に手間がかかる、最新版がどれか分かりにくい、スタッフに周知するのに時間がかかるといった課題がある。
- 「勤務表」は、**管理者が月間のシフトをまとめて作成し、スタッフ全員がいつでも最新のシフトを確認できる**ツールとする。
- 目的は「シフト作成の手間削減」と「情報共有の即時化」。給与計算や勤怠打刻(実際に何時に出社したか)はMVPでは扱わない。

## 2. 対象ユーザー
- **管理者(店長・シフト担当者)**: スタッフ一覧を管理し、日付ごとに勤務時間帯や休みを割り当てる人。シフトの新規作成・修正を行う唯一の権限者。
- **スタッフ(一般社員・アルバイト等)**: 自分や他メンバーのシフトを閲覧する人。編集は行わない。ITに詳しくない前提で、見るだけで完結する画面にする。
- 対象外(MVPでは想定しない): 出退勤の実打刻・実績記録、給与計算、有給申請などの承認フロー。

## 3. 必須機能(MVP)
1. **スタッフ一覧の登録**
   - 管理者がスタッフの氏名を登録・編集・削除できる(シンプルな一覧管理)。
2. **シフトの作成・編集(管理者のみ)**
   - 日付 × スタッフのマス目に、勤務時間帯(例: 9:00-18:00)または「休み」を入力できる。
   - 既存のシフトを修正・削除できる。
3. **月間カレンダー表示**
   - 1ヶ月分のシフトをカレンダー形式または表形式で一覧表示する。
   - 日付ごとに「誰が何時から何時まで勤務か」が一目でわかる表示にする。
4. **スタッフ個人ビュー**
   - スタッフ本人の名前で絞り込み、自分の月間シフトだけを見やすく表示できる。
5. **権限の区分(簡易)**
   - 「管理者モード」と「閲覧のみモード」を切り替える程度の簡易な区分とする(MVPでは本格的なログイン認証は行わず、パスワード等の簡易な仕組みで十分とする)。
6. **データの複数人・複数端末共有** ★今回の要件の核心
   - 管理者がシフトを作成・更新すると、スタッフが別の端末(スマホ・PC)から見たときに同じ内容が確認できること。
   - 具体的な実装方式は「6. 開発者への申し送り事項」を参照。

## 4. 今後の拡張候補(MVPには含めない)
- 出退勤の実打刻・実績記録(当初案。将来的にシフトツールと連携させる案もあり)
- スタッフからの休み希望・シフト交代リクエスト機能
- シフトの自動作成・人員不足の自動アラート
- LINE・メール等への自動通知(シフト確定時にスタッフへ通知)
- 部署・店舗をまたぐ複数チームの一括管理
- 給与計算・人件費集計との連携
- スタッフごとのログインアカウント(本格的な認証)

## 6. 開発者への申し送り事項

### 最重要課題: 複数人・複数端末でのデータ共有について
- 会社のこれまでのツール(bv-prr-tool、RPA(CSV→Excel)、風袋管理データツール等)は、いずれも**サーバーを持たずブラウザ内(localStorage/IndexedDB)で完結する単体HTML構成**をGitHub Pagesで公開するスタイルを採用してきた。
- しかし今回は「管理者が作ったシフトを、別のスタッフが別の端末で見られる」ことが必須要件であり、**ブラウザ単体保存の方式では実現不可能**(データが端末内に閉じてしまうため)。何らかの形で外部にデータを置く仕組みが必要になる。
- 実装方式として以下の3案を検討した。

| 案 | 概要 | メリット | デメリット |
|---|---|---|---|
| **A. Firebase Realtime Database / Firestore(無料枠)** | Googleが提供するクラウドDBをJSからそのまま読み書きする。サーバーコードの開発・運用は不要。 | 複数端末でほぼリアルタイムに同期。無料枠で小規模利用なら十分。既存の「単体HTML+クライアントサイドJS」構成に近い形で実現できる。 | 最初にFirebaseプロジェクトの作成(Googleアカウント)とAPIキー設定という一手間が発生。 |
| **B. Googleスプレッドシートをデータストアにする** | シフトデータをスプレッドシートに読み書きする(Apps Script Web App等を経由)。 | 経営者がスプレッドシートを直接開いて中身を確認・手直しできる安心感がある。RPA(CSV→Excel)ツールでExcel/CSVを扱ってきた経緯とも相性が良い。 | Apps ScriptのWeb App公開設定やアクセス権限の管理がやや煩雑。同時編集時の競合や反映タイムラグが発生しやすい。 |
| **C. エクスポート/インポート(ファイルやURL)による疑似共有** | 管理者がシフトデータをファイル(JSON等)やURLパラメータとして書き出し、スタッフ側で読み込む。 | 追加サービス契約が一切不要。実装コストが最も低い。 | リアルタイム共有ではなく、更新のたびに管理者が配布し直す必要がある。「見るだけで完結」というスタッフ側の使い勝手を大きく損なう。 |

- **推奨: A. Firebase Realtime Database(またはFirestore)の無料枠を採用する。**
  - 理由1: 今回の要件は「打刻データの記録」ではなく「シフトを見る・共有する」ことが主目的であり、スタッフが自分の端末を開いた瞬間に最新のシフトが反映される体験がツールの価値そのものである。案Cではこの価値を満たせない。
  - 理由2: 案Bはスプレッドシート閲覧という安心感がある一方、Web Appの公開設定・認可まわりで非エンジニアの経営者が将来メンテナンスに詰まりやすい。Firebaseはコンソール上のセキュリティルール設定だけで「管理者のみ書き込み可・全員閲覧可」という権限分離がシンプルに実現できる。
  - 理由3: サーバー運用コストがかからず(無料枠で小規模利用は十分)、既存ツール群と同じく「静的HTML + JS」の構成をほぼ維持できるため、GitHub Pagesでの公開スタイルからの逸脱が最小限で済む。
  - 初期セットアップ(Firebaseプロジェクト作成・APIキー取得)は開発者側で一度だけ行い、経営者側の追加作業は発生しない想定。
- 案Bは、将来「経営者自身がスプレッドシートを直接編集したい」という要望が出た場合の拡張候補として保留する。

### その他の申し送り事項
- 権限区分はMVPでは簡易なもの(例: 管理者モードに入る際に共通パスワードを入力する程度)でよい。本格的なスタッフ個別ログインは拡張候補とする。
- 勤務時間帯の入力はテキスト自由入力ではなく、開始・終了時刻をプルダウンや時刻入力で選ばせる形にし、表記ゆれ(例: "9時-18時" と "09:00-18:00" が混在する)を防ぐこと。
- 「休み」「有給」などのステータスは時間帯とは別に選べるようにし、シフト表内で色分け等により視覚的に区別できるとよい。
- 個人情報(氏名・勤務時間)をクラウドに保存する構成となるため、QAレビューではFirebaseのセキュリティルール(誰が読み書きできるか)を重点的に確認すること。
- 将来「出退勤の実打刻」機能を追加する場合、本ツールのスタッフ一覧・シフトデータと連携できるとよい(初版spec.mdで検討していた勤怠記録機能は、拡張候補として残す)。

## 7. 経営者確認事項への回答(2026-08-11)

1. **データ共有方式**: Firebase Realtime Database/Firestore(無料枠)採用で確定。
2. **権限区分**: 簡易な共通パスワード方式で確定(管理者モードに入る際に共通パスワードを入力)。スタッフ個別ログインは引き続き拡張候補。
3. **勤務時間帯の入力粒度**: 30分単位。ステータスは「勤務時間帯」「休み」に加えて「有給」「遅刻予定」を選択肢に追加する。
4. **スタッフ人数規模**: 10〜30名程度。Firebase無料枠(Spark plan)で十分に収まる規模。

以上の回答を踏まえ、developerエージェントへ実装を引き継ぐ。
