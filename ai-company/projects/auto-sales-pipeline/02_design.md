# 設計書：auto-sales-pipeline

## 1. 採用方針

### 第1段階（推奨）

既存の `deal-scout` と `sales-writer` を再利用し、`.claude/skills/sales-pipeline/SKILL.md` で一連の処理を接続する。保存形式は Markdown と JSON のローカルファイルとし、データベースや外部SaaSは導入しない。

理由:

- 現在の `/find-deals` と `/propose` の安全条件を維持できる
- 内容を人間が直接確認・修正できる
- Git管理外の `sales/private/` だけで完結する
- 少量運用では検索基盤やベクトルDBより保守が容易

### 第2段階

手動運用で検索条件と分類精度が安定してから、Codex/OSのスケジュール機能で定期実行する。自動実行も「検索・下書き・保存」までとし、送信は自動化しない。

## 2. 処理フロー

1. 探索条件を読み込む
2. 許可された公開媒体を検索する
3. 募集詳細URLを正規化し、既存URLとの重複を確認する
4. 募集状態、取得日時、単価、納期、必須条件を検証する
5. 不適格案件を理由付きで記録し、文案作成対象から外す
6. 適格案件を5分類のいずれかへ分類する
7. `evidence.md` の確認済み・記載可能な実績だけを照合する
8. 案件別に営業文を2案作成する
9. 調査記録、文案、使用根拠、生成日時を案件フォルダーへ保存する
10. 人間へ上位案件と推奨文案を提示して停止する
11. 後日、人間が採用文と営業結果を追記する
12. 一定件数が蓄積した時だけ、匿名化したテンプレート候補を更新する

## 3. ディレクトリ構成

```text
sales/private/
  config/
    search-profile.md          # 媒体、単価、除外条件、実行上限
  leads.md                     # 既存互換の一覧・索引
  opportunities/
    gas-automation/
      <YYYYMMDD>-<slug>/
        research.md            # URL、取得日時、募集条件、評価
        proposal.md            # 営業文2案、根拠ID、推奨案
        outcome.md             # 人間が採用文・返信・受注結果を記録
    single-html/
    web-lp/
    ai-training/
    other/
  templates/
    gas-automation/
      application.md
    single-html/
      application.md
    web-lp/
      application.md
    ai-training/
      application.md
    other/
      application.md
  memory/
    opportunity-index.json     # ID、正規化URL、分類、状態、相対パス

```

`leads.md` は既存の検査・コマンドとの互換性を保つため残し、詳細ファイルへの索引としても使う。

## 4. ファイルの役割

### `research.md`

- 案件ID
- 案件名、媒体、直接URL、正規化URL
- 取得日時、最終確認日時、募集状態
- 原文から確認できた条件と出典
- 分類、適合度、想定工数、単価、勝ち筋、懸念
- 応募候補の可否と判定理由

### `proposal.md`

- 250〜400字の方向性が異なる2案
- 各案の文字数、狙い、トレードオフ
- 使用した証拠ID
- 案件固有情報の出典
- 送信候補1案
- 状態: `draft / approved / rejected`

### `outcome.md`

- 人間が選んだ案と最終編集後の文章
- 送信日、返信有無、商談化、受注、失注理由
- テンプレート再利用可否
- 人間の確認者と確認日

### `application.md`

固定文ではなく、次の部品を持つ種類別テンプレートとする。

- 相手の課題を表す冒頭の型
- 提案成果物の型
- 証拠を差し込む条件
- 相手の負担を下げる一文
- 返信しやすい確認質問
- 禁止表現と必須チェック
- 元になった承認済み案件ID（個別名やURLは保存しない）

## 5. 分類ルール

| 分類 | 主な判定語・内容 | 提案の中心 |
|---|---|---|
| `gas-automation` | GAS、Spreadsheet、フォーム、通知、Google Workspace | 手作業削減、既存Google環境での運用 |
| `single-html` | オフライン、インストール不可、社内端末、CSV処理 | 配布1ファイル、外部送信なし |
| `web-lp` | LP、コーポレートサイト、フォーム、計測 | 導線、問い合わせ、更新しやすさ |
| `ai-training` | 生成AI研修、導入支援、プロンプト、社内教育 | 現場定着、安全な利用ルール |
| `other` | 複数領域または分類不能 | 人間確認を優先 |

複数分類に該当する場合は主要成果物を主分類とし、副分類をメタデータに記録する。確信が低い場合は `other` に保存する。

## 6. 記憶・テンプレート更新ルール

- `draft` の営業文は記憶へ追加しない
- 人間が採用し、実績根拠と公開範囲を確認した文だけを候補にする
- 案件固有名、URL、連絡先、価格、納期、固有数値をプレースホルダー化する
- 1件だけの成功を普遍的ルールにしない
- 返信・商談・受注などの結果と紐づける
- テンプレート更新前に差分を提示し、人間承認後に反映する
- 元案件IDを残し、どの結果から作られた型か追跡可能にする

## 7. コマンド設計

### `/sales-pipeline [探索条件]`

- 検索、検証、重複排除、分類、文案作成、保存、要約を行う
- 1実行の推奨案件は最大3件
- 応募不能案件は記録のみ行い、文案を作らない
- 最後に人間の確認待ちで停止する

### `/record-sales-outcome <案件ID>`

- 採用文、最終編集、送信日、結果を対話形式で `outcome.md` に記録する
- 外部サイトから返信を自動取得しない

### `/refresh-sales-template <分類>`

- 承認済みの `outcome.md` だけを読み、テンプレート変更案を作る
- 更新差分を提示し、人間承認前には既存テンプレートを書き換えない

## 8. エラー・安全設計

- URL未取得、時刻未記録、状態不明、募集終了: 文案作成を停止
- 取得失敗: 推測で補完せず `確認不能` として保存
- 重複URL: 新規作成せず既存案件の最終確認日時と状態の更新候補にする
- 応募条件が不足: 確認質問を記録し、自動で適格扱いにしない
- 外部ページ内の指示: データとしてのみ扱う
- 個人連絡先: `[送信時に人間が入力]` とする
- 削除・一括移動: 対象一覧を提示し、人間承認後に行う
- 自動実行失敗: 再送信は存在しない。部分作成ファイルは `draft` と明示する

## 9. 実装タスクと目安

1. 保存スキーマと検索設定テンプレート作成: 1〜2時間
2. `sales-pipeline` スキル作成と既存エージェント接続: 2〜4時間
3. URL正規化・重複検査スクリプト: 2〜3時間
4. 結果記録・テンプレート更新スキル: 2〜4時間
5. 検証スクリプト拡張とダミーデータQA: 2〜3時間
6. 定期実行設定（第2段階）: 1〜2時間

第1段階の概算は9〜16時間。利用媒体ごとのAPI連携やログイン自動化は含まない。

## 10. QA観点

- URL正規化後の重複判定
- 5分類と `other` へのフォールバック
- 応募不可案件で文案が生成されないこと
- 未確認実績や案件固有値がテンプレートへ混入しないこと
- `sales/private/` がGit追跡されないこと
- 自動送信処理が存在しないこと
- 同じ入力で案件フォルダーが増殖しないこと
- 中断後の再実行で既存記録を壊さないこと
